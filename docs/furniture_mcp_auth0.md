# Furniture MCP: локальная реализация для Auth0

Состояние на 16 октября 2026: пользователь выбрал Auth0 Free. Реализована **ресурсная часть** OAuth и Streamable HTTP над локальным архивом. Tenant, приложение Auth0, реальные ключи, grants, подключение ChatGPT и production-размещение не создавались. Это завершённый локальный код, но не подтверждение реального login/consent/refresh или доступности функций на конкретном tenant.

Эта реализация заменяет ожидание выбора AS из [предыдущей записки](furniture_mcp_oauth_decision.md). Используется проверка JWT по публичному JWKS; предложенная ранее online introspection не реализована и не требуется для первого локального варианта. Ограничения отзыва приведены ниже.

## Граница процесса

`furniture_mcp` запускается отдельно от Flask/Gunicorn бухгалтерии, в отдельном Python-окружении. Он импортирует только безопасные configuration/store модули архива, официальный MCP SDK и библиотеки верификации. Он не импортирует `web_app`, `UserDatabase`, Gemini, Poster, обработчик входящих событий или media worker.

MCP читает существующий SQLite через `mode=ro` и `PRAGMA query_only`, не создаёт отсутствующую БД, не инициирует скачивания и не обновляет очередь. Каждый запрос фильтруется одновременно по назначенному `instance_id` и разрешённым чатам. Каталог архива должен находиться вне приложения, быть приватным и доступным серверу только для чтения. Рекомендуется также read-only mount на уровне ОС; настройки deployment здесь не менялись.

У сервера нет `/authorize`, `/token`, `/register`, обработки пароля, отправки сообщений и методов записи. Единственный исходящий запрос процесса — GET публичного JWKS по фиксированному адресу доверенного issuer. Он не содержит токен доступа, `sub`, содержимое чатов, телефоны, query-параметры или cookies. Переписки и файлы будут передаваться MCP-клиенту только после отдельной активации и его авторизованного запроса.

## Проверка авторизации

- Только RS256 и ключи из `<issuer>.well-known/jwks.json`; URL из JWT никогда не используются. PyJWT проверяет подпись, точные `iss`/`aud`, `exp`, `iat`, при наличии `nbf`. Максимальная длительность `exp - iat` — 900 секунд, без допуска на рассинхронизацию часов.
- Обязательны конкретный `sub` владельца и точный `azp` заранее зарегистрированного ChatGPT-клиента. Другой вошедший пользователь не получает доступ. Поддерживается **Auth0 token profile**; RFC 9068 profile с `client_id` вместо `azp` сейчас не поддерживается.
- `aud` может быть строкой или массивом; он должен включать канонический MCP URL. ID token с audience клиентского приложения не подходит. Scopes берутся из `scope`, не из email, роли или списка `permissions`.
- Весь HTTP endpoint требует `furniture.messages:read`; вложение дополнительно требует `furniture.attachments:read`. Права повторно проверяются в каждом обработчике инструмента. Аннотации только описывают поведение и не заменяют проверку.
- JWKS: максимум 1 MiB / 32 ключа, timeout 5 секунд, без redirects и environment proxy; публичные ключи кешируются 300 секунд. Неизвестный `kid` вызывает не более одной попытки обновления за 30 секунд. После истечения кеша ошибка Auth0 закрывает доступ. Проверки токенов не кешируются.
- Неверный/отсутствующий токен — HTTP 401 с discovery challenge; недостаточный общий scope — 403. Для отсутствующего scope вложения возвращается MCP error с `mcp/www_authenticate`.

Основание: [Auth0 validation](https://auth0.com/docs/secure/tokens/access-tokens/validate-access-tokens), [token profiles](https://auth0.com/docs/secure/tokens/access-tokens/access-token-profiles), [JWKS](https://auth0.com/docs/secure/tokens/json-web-tokens/json-web-key-sets), [OpenAI auth](https://developers.openai.com/plugins/build/auth). Лимиты и привязка к одному владельцу — локальная политика этого проекта.

## Инструменты и пределы

| Инструмент | Вход и результат |
| --- | --- |
| `list_chats` | Сохранённые разрешённые чаты, число сообщений и время последнего приёма; до 50 за страницу, `after_chat_id`. Названия групп не выдумываются. |
| `search_messages` | Литеральный поиск без учёта регистра по сохранённому тексту/подписям, запрос 2–200 символов; опциональный `chat_id`, `after_id`, 20 результатов по умолчанию / 50 максимум. Фрагменты до 1000 символов и `text_truncated`. |
| `read_message` | Один числовой ID строки архива; текст и безопасные метаданные вложения. При ограничении текста возвращается `text_truncated=true`. |
| `read_attachment` | Один opaque ID готового вложения, исходный файл до 2 MiB. Изображение — MCP image; PDF — встроенный binary resource. Больший файл — `too_large`, небезопасный/повреждённый — `unavailable`; скачивание и OCR не запускаются. |

Все четыре инструмента объявляют `readOnlyHint=true`, `destructiveHint=false`, `idempotentHint=true`, `openWorldHint=false` и OAuth securitySchemes, включая compatibility mirror. Список инструментов проверяется в сыром HTTP JSON: официальный SDK 2.3.0 переносит нестандартное поле через публичный middleware API, помеченный SDK как provisional; обновление SDK требует повторной проверки.

Поиск ограничен 64 KiB полного обычного HTTP JSON-ответа, одно сообщение — 128 KiB: внутренние бюджеты 20/40 KiB оставляют место для текстового и структурированного представления. Пагинация продолжает с последнего действительно выданного сообщения. SQL ограничен временем и количеством VM-шагов; большая история может потребовать отдельного индекса или поиска — превышение бюджета даёт ошибку, а не неполный ответ без предупреждения. JSON-RPC request ID и служебные поля также занимают место; входной запрос ограничен 32 KiB.

Вложения проверяются по приватным правам, владельцу, типу файла, ссылкам, размеру и SHA-256. Публичных URL, локальных путей и исходных download URL в ответах нет. Прочитанные изображения/PDF не проходят антивирус, OCR или обработку здесь. Отображение PDF конкретным клиентом необходимо проверить при E2E.

## Явная конфигурация

Без `FURNITURE_MCP_ENABLED=true` приложение отвечает 404 и не читает архив/JWKS. При включении неполная конфигурация запрещает запуск. `.env` автоматически не загружается. Существующие static bearer credentials архива не принимаются и этому процессу не нужны.

| Переменная | Значение при будущей настройке |
| --- | --- |
| `FURNITURE_MCP_ENABLED` | Только явное `true` включает сервер. |
| `FURNITURE_MCP_AUTH0_ISSUER` | Точный доверенный HTTPS issuer с завершающим `/`. |
| `FURNITURE_MCP_RESOURCE_URL` | Канонический HTTPS URL с путём `/mcp`; одновременно Auth0 API Identifier/audience. |
| `FURNITURE_MCP_AUTH0_CLIENT_ID` | Client ID одного заранее зарегистрированного приложения ChatGPT. Это не client secret. |
| `FURNITURE_MCP_OWNER_SUB` | Проверенный неизменяемый Auth0 `sub` владельца; не email и не client ID. |
| `FURNITURE_MCP_CHAT_IDS` | Разрешённые этому владельцу ID чатов через запятую; без `*`. |
| `FURNITURE_CHAT_IDS` | Серверный список разрешённого приёма архива. |
| `FURNITURE_READ_CHAT_IDS` | Серверный список чтения архива, подмножество списка приёма. |
| `FURNITURE_INSTANCE_ID` | Единственный допустимый инстанс записей архива. |
| `FURNITURE_STORAGE_DIR` | Абсолютный приватный каталог существующего архива вне дерева приложения. |
| `FURNITURE_MCP_MIN_ISSUED_AT` | Необязательная локальная отсечка Unix seconds, по умолчанию 0. JWT с меньшим `iat` отклоняется после перезапуска. |

Список владельца должен быть непустым подмножеством read-списка, read-список — списка приёма; каждый максимум 100 чатов. Эффективное право — их пересечение. Не передавать сюда `.env` бухгалтерии или GREEN-API ключи. Секрет клиента хранится в настройке OAuth-подключения ChatGPT, не в MCP-процессе. Пример фиктивной конфигурации — [furniture_mcp.env.example](furniture_mcp.env.example).

## Локальный запуск и проверки

Python 3.11+; локальные проверки выполнены на Python 3.12. Не устанавливать зависимости в окружение финансового приложения:

```sh
python3 -m venv /tmp/furniture-mcp-venv
/tmp/furniture-mcp-venv/bin/python -m pip install -r requirements-furniture-mcp.txt
/tmp/furniture-mcp-venv/bin/python -m pip install pytest==9.1.1
/tmp/furniture-mcp-venv/bin/python scripts/run_furniture_mcp_tests.py
```

Offline runner очищает окружение и запрещает сетевые сокеты/DNS. Тесты используют временные RSA ключи, фиктивный `.invalid` issuer, MockTransport JWKS, локальный ASGI HTTP и синтетический архив. Никакие Auth0 grants в тестах не выдаются. Тесты покрывают discovery, обе эпохи MCP, негативную авторизацию, scope/instance изоляцию, чтение файлов и неизменность архива. Точный итог запуска сохраняется отдельно в отчёте проверки.

Ручной локальный запуск после явной конфигурации: `python -m furniture_mcp`. Он слушает только `127.0.0.1:8001`, отключает access log и доверие proxy headers. Для будущего HTTPS reverse proxy должен сохранять канонический Host; origin допускается только канонический origin MCP. Health checks не должны ослаблять host/auth проверки. Интеграция с конкретным хостингом пока не проверена.

## Будущая настройка Auth0 — пока не выполнена

1. После отдельного разрешения создать/выбрать tenant Auth0 Free, проверить доступность нужных настроек и действующие лимиты. Назначить владельца и защищённое администрирование. Переписки/номера не включать в metadata, Actions, scopes или identity claims.
2. Включить **Resource Parameter Compatibility Profile**. Зарегистрировать API с Identifier, точно равным `FURNITURE_MCP_RESOURCE_URL`; RS256, **Auth0 token profile**, срок access token не более 900 секунд (включая применимый browser flow). Добавить два указанных read scopes. Scope-гранты сами по себе не заменяют локальную проверку owner sub.
3. Предварительно зарегистрировать отдельный клиент ChatGPT. Разрешить Authorization Code с обязательным PKCE S256; не включать открытый DCR, wildcard callbacks, password grant или client-credentials для доступа к архиву. Параметры authentication method согласовать с фактической формой подключения.
4. Включить Include Issuer in Authorization Responses и проверить discovery (`code_challenge_methods_supported` содержит S256). Точный callback взять из управления **создаваемым** подключением ChatGPT; затем зарегистрировать только его. Не использовать догаданный callback из примеров документации.
5. Первоначально не включать `offline_access`/refresh. Если для работы клиента потребуется длительный доступ, согласовать отдельно Allow Offline Access, refresh rotation, сроки, отзыв и хранение; проверить реальный flow. MCP-процесс refresh tokens не получает и не хранит.

Auth0 трактует `resource` как audience при включённом профиле, если явный `audience` не передан; при двух параметрах приоритет у `audience`. Поэтому неверный audience обязан отклоняться нашим verifier. [Resource profile](https://auth0.com/ai/docs/mcp/guides/resource-param-compatibility-profile), [PKCE](https://auth0.com/docs/api/authentication/authorization-code-flow-with-pkce/authorize-with-pkce), [OpenAI подключение](https://developers.openai.com/api/docs/guides/custom-mcp-server).

## Активация и откат — отдельное разрешение

1. Проверить diff, тесты и конфигурацию. Согласовать реальные чаты/инстанс/owner sub и хранение архива; первоначальный сбор чатов не включается этим MCP-кодом.
2. Выбрать размещение отдельного процесса, TLS, фиксированный URL и доступ к тому архива только для чтения. Независимые Railway-сервисы/реплики не считаются автоматически имеющими общий локальный SQLite. Не запускать финансовые миграции для MCP.
3. После разрешения настроить Auth0 и runtime secrets в соответствующих интерфейсах, не в чате. Публикация кода, включение endpoint и создание реального подключения требуют отдельной активации.
4. Проверить публичные metadata/401 и отсутствие открытых файлов; затем реальный PKCE, callback, issuer/resource, consent, один согласованный текст/файл, запрет чужого пользователя/чата/инстанса. Только после этого утверждать совместимость с конкретным ChatGPT-подключением.
5. Проверить отключение и повторный отказ. На данном этапе нет подтверждения E2E, реального refresh, отзывов Auth0, TLS/reverse proxy, production Python 3.11 или общего тома.

Для немедленной остановки локального доступа остановить **только MCP-процесс** либо выставить `FURNITURE_MCP_ENABLED=false` и перезапустить его. Это не меняет webhook/GREEN-API/бухгалтерию. Удаление owner/chat из конфигурации также вступает в силу после перезапуска. Архив не удалять и схему не откатывать: MCP её не менял. При откате версии сначала выключить процесс, затем вернуть предыдущую сборку и проверить закрытый endpoint.

Отозвать OAuth grant/refresh отдельно в Auth0 и отключить подключение ChatGPT. Уже выданный JWT может работать до `exp` (не более 15 минут от выдачи), а кеш JWKS не гарантирует мгновенного обнаружения отзыва ключа. `MIN_ISSUED_AT` отсекает старые JWT, но **не запрещает выпуск новых** по ещё действующему grant. Для полного немедленного запрета использовать выключение MCP/owner-доступа и отзыв grant. Management API Enterprise-функции не являются зависимостью реализации. [Auth0 отзыв](https://auth0.com/docs/secure/tokens/refresh-tokens/revoke-refresh-tokens), [refresh rotation](https://auth0.com/docs/secure/tokens/refresh-tokens/refresh-token-rotation).
