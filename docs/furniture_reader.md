# Чтение разрешённых мебельных чатов

Модуль предназначен для сохранения новых событий из явно разрешённых WhatsApp-чатов и выдачи их через API только для чтения. Для мебельных событий не должны вызываться Gemini, отправка сообщений, создание расходов, поставок или бухгалтерских черновиков. Действующий маршрут группы «Ассистент» сохраняется.

Публикация, изменение настроек Railway/GREEN-API и активация в production в рамках этой подготовки не выполнены. Подключение выбранного ассистента также не проверено. Наличие кода и успешные локальные тесты ещё не означают, что постоянная интеграция работает. Для работы без Mac нужны развёрнутый сервер, постоянное хранилище, резервные копии, наблюдение за ошибками и подтверждённый коннектор.

Контракт ниже сверяется с [config.py](../furniture_reader/config.py), [service.py](../furniture_reader/service.py), [routes.py](../furniture_reader/routes.py), [store.py](../furniture_reader/store.py), [media.py](../furniture_reader/media.py) и [автономным запуском тестов](../scripts/run_furniture_tests.py).

## Разделение данных и обработки

Общий обработчик входящих событий выбирает маршрут по точному идентификатору чата. Мебельный маршрут сохраняет событие в отдельный SQLite-архив. Он не использует таблицы `whatsapp_jobs`, `whatsapp_batches`, историю бухгалтерского ассистента или `UserDatabase` как хранилище читателя.

Список мебельных чатов и действующий бухгалтерский список `WHATSAPP_GROUP_ID` должны быть непустыми и не пересекаться. Бухгалтерский маршрут имеет приоритет: событие чата из `WHATSAPP_GROUP_ID` возвращается прежнему обработчику даже при пересечении списков или другой ошибке настройки мебельного модуля. При пересечении весь мебельный архив считается ненастроенным; двойной обработки одного события нет. Пустой бухгалтерский список также блокирует мебельный приём. Модуль не исправляет и не меняет `WHATSAPP_GROUP_ID` автоматически.

Разрешения приёма и чтения различаются: событие может архивироваться из `FURNITURE_CHAT_IDS`, а API выдаёт только группы из `FURNITURE_READ_CHAT_IDS`. Для чтения второй список должен быть непустым подмножеством первого. Ошибка в списке чтения закрывает API с кодом `503`, но не останавливает правильно настроенный приём. Названия групп не заменяют их идентификаторы. Пустой список не означает доступ ко всем чатам.

Сохраняются только отобранные поля события, без полного исходного JSON и служебных полей имени/телефона отправителя. Текст сообщения и имя файла могут сами содержать персональные сведения. Дедупликация выполняется по `(instance_id, chat_id, message_id)`; повтор не перезаписывает сообщение или вложение. Архив принимает события `incomingMessageReceived`, `incomingFileMessageReceived`, `outgoingMessageReceived`, `outgoingFileMessageReceived`. Направление `outgoing` означает наблюдение уже отправленного сообщения, а не отправку модулем.

## Конфигурация

Переменные задаются в закрытых настройках окружения сервиса. Секреты, реальные идентификаторы чатов и значения действующих учётных данных не добавляются в репозиторий или этот документ.

| Переменная | Назначение |
| --- | --- |
| `FURNITURE_READER_ENABLED` | По умолчанию выключен. Включает только значение `true` без учёта регистра. |
| `FURNITURE_CHAT_IDS` | Точные ID разрешённых для приёма чатов через запятую; пробелы вокруг элементов удаляются. |
| `FURNITURE_READ_CHAT_IDS` | Точные ID разрешённых для чтения чатов через запятую; непустое подмножество `FURNITURE_CHAT_IDS`. |
| `FURNITURE_INSTANCE_ID` | Ожидаемый идентификатор источника GREEN-API; входящее событие должно ему соответствовать. |
| `FURNITURE_READ_TOKEN_SHA256` | SHA-256 отдельного токена чтения: ровно 64 шестнадцатеричных символа в нижнем регистре. |
| `FURNITURE_WEBHOOK_TOKEN_SHA256` | SHA-256 другого токена входящих событий в том же формате; хеши должны различаться. |
| `FURNITURE_STORAGE_DIR` | Обязательный абсолютный путь к закрытому постоянному каталогу архива и вложений вне всего дерева приложения. |
| `FURNITURE_MEDIA_ENABLED` | По умолчанию выключен; включается значением `true` без учёта регистра. |
| `FURNITURE_MEDIA_HOSTS` | Точные DNS-имена через запятую, приводятся к нижнему регистру. Без схемы, путей, порта, IP-адресов или масок поддоменов. |
| `FURNITURE_MEDIA_MAX_BYTES` | Максимальный размер файла. По умолчанию `10485760` (10 MiB), допустимый рабочий диапазон от `1` до `26214400` (25 MiB). |

Настройки читаются при регистрации модуля: после изменения окружения требуется перезапуск процесса. Если медиа включены, но список хостов пуст либо лимит размера недопустим, загрузчик не берёт задания. Приём и GET API при этом могут работать, а вложения оставаться `pending`. Нечисловое значение лимита преобразуется в `0`, что также останавливает загрузчик. Это нужно выявить при активации и мониторинге, а не считать успешным запуском медиа.

Для каждого назначения нужен свой случайный токен достаточной энтропии, длиной от 32 до 512 символов без пробельных символов. В конфигурации сервера задаётся только его SHA-256; клиент передаёт исходный токен по HTTPS в заголовке `Authorization: Bearer …` с указанным регистром `Bearer`. Хеш не передаётся вместо токена. Не помещайте токены в URL, примеры команд, логи или переписку. Токен читателя не является `apiTokenInstance` и не предоставляет полный доступ к GREEN-API. Сессия владельца сайта и Telegram-авторизация не заменяют этот токен.

Возможность отправителя передавать нужный заголовок необходимо подтвердить до включения. Действующий вход `POST /api/whatsapp/webhook` сохраняется; отдельного мебельного webhook-URL нет. Проверка мебельного токена выполняется после выделения бухгалтерских чатов и не меняет их прежнюю авторизацию. Не объявляйте интеграцию готовой, пока реальная доставка заголовка не проверена.

### Отказы и выключенный режим

| Ситуация | Результат |
| --- | --- |
| `FURNITURE_READER_ENABLED` выключен | API читателя возвращает `404`; мебельный архив и загрузчик не работают. Webhook полностью следует прежнему обработчику и его бухгалтерским фильтрам. |
| Включён модуль, чат явно бухгалтерский | Прежний бухгалтерский маршрут, включая случай пересечения списков. |
| Включён модуль, чат отсутствует в обоих списках | `200 Ignored non-target chat`, без архивирования и без бухгалтерской обработки. |
| Мебельный чат, но основные настройки неверны | `503 Furniture reader not configured`; перехода в бухгалтерский обработчик нет. |
| Мебельный чат, неверный или отсутствующий webhook-токен | `401 Unauthorized`. |
| Мебельный чат, другой instance | `403 Unexpected instance`. |
| Успешное сохранение / повтор | `200 Archived` / `200 Duplicate`. |
| Неверные поля события / ошибка записи архива | `400 Invalid furniture event` / `503 Furniture archive unavailable`, без бухгалтерского fallback. |

Неизвестные типы webhook игнорируются с `200`. Основные настройки считаются допустимыми только при включённом флаге, непустых непересекающихся списках приёма и бухгалтерии, заданном instance, двух разных корректных хешах и допустимом пути хранения. Ошибки доступа к диску могут проявиться уже при операции с архивом. Нормализатор ограничивает сериализованный JSON события 1 MiB, а извлечённый текст или подпись — 32 768 символами; это отдельные ограничения от размера файла.

## Подготовка развёртывания

1. Зафиксировать проверенную версию приложения и действующую конфигурацию бухгалтерского маршрута в защищённом эксплуатационном учёте. Не копировать секреты в отчёт или Git.
2. Проверить непересекающиеся списки групп и ожидаемый GREEN-API instance. Не расширять бухгалтерский список ради мебельных сообщений.
3. Подготовить постоянный том Railway и отдельный закрытый каталог для `FURNITURE_STORAGE_DIR`. Не использовать `static`, каталог загрузок сайта с публичной раздачей, бухгалтерскую БД, `/tmp` или временный слой контейнера.
4. Создать закрытый подкаталог на томе для сервисного пользователя: каталоги `0700`, файлы `0600`. Код проверяет владельца и отсутствие доступа группы/остальных, отклоняет символьные ссылки, жёсткие ссылки на файлы и чужую SQLite-БД, не исправляет права существующего каталога автоматически. Путь должен быть абсолютным, отличаться от `/` и находиться вне всего дерева приложения. Архив хранится как `archive.sqlite3`, файлы — в `media/`. При скачивании вложения повторно проверяются владелец, права, тип файла, число ссылок и размер. Проверить сохранность при перезапуске и обновлении. Не считать локальный SQLite-файл общим хранилищем независимых реплик с разными томами.
5. Настроить согласованные резервные копии SQLite вместе с вложениями и проверить восстановление в изолированное хранилище. Простое копирование работающего файла SQLite без учёта журнала не считается проверенной резервной копией.
6. Определить срок хранения, доступ к резервным копиям, контроль свободного места и порядок удаления данных. Автоматическая очистка старых сообщений/файлов и API удаления в этом модуле не реализованы.
7. Настроить наблюдение за приёмом событий, доступностью API, ошибками загрузки вложений и заполнением тома. Проверка HTTP-доступности сайта сама по себе не доказывает, что архив пополняется.
8. Развернуть проверенную версию с `FURNITURE_READER_ENABLED=false` и `FURNITURE_MEDIA_ENABLED=false`. Изменение production и активация выполняются отдельным согласованным этапом.

## Проверка и включение

Сначала выполнить автономные тесты на синтетических событиях и временной БД из подготовленного локального окружения:

```sh
.venv/bin/python -u scripts/run_furniture_tests.py
```

Этот запуск очищает унаследованное окружение, отключает загрузку dotenv и автоматическую загрузку pytest-плагинов, запрещает DNS и сокетные подключения и использует временный каталог. Он не запускает `start_server` и не загружает production-учётные данные. Не заменяйте его обычным запуском приложения для проверки.

Проверить разрешённый и запрещённый чат, неверный instance, отсутствие и подмену обоих токенов, пересечение списков, повтор одного события, пагинацию и отказ доступа к чужому вложению. Проверка мебельной ветки должна также подтверждать отсутствие вызовов бухгалтерской очереди и отправки сообщений. Локальные тесты не подтверждают живую доставку GREEN-API, том Railway или работу коннектора ассистента.

После проверки конфигурации включить мебельный контур, оставив медиа выключенными. Убедиться на новом согласованном входящем событии, что оно доступно читателю и не породило бухгалтерскую задачу, черновик или исходящий ответ. Не запускать повторную обработку старых накладных для проверки. Работу группы «Ассистент» проверять по разрешённым наблюдениям существующего процесса, без создания тестовых финансовых операций.

Отдельно проверить отказ доступа к неразрешённой группе и невозможность выполнять изменяющие запросы через API читателя. До завершения проверки не выдавать его токен клиенту, которому не требуется доступ к этим сообщениям.

Медиа включаются отдельным шагом после проверки точных разрешённых хостов, ограничения размера и обработки ошибок. Поддерживаются JPEG, PNG, WebP и PDF; MIME ответа должен соответствовать сигнатуре файла. Разрешён только HTTPS на порту 443, без перенаправлений и обращения к частным/служебным IP. Загрузчик не передаёт GREEN-API credentials, не использует прокси из окружения и ограничивает одну загрузку 10 секундами. Проверка сигнатуры не является антивирусной проверкой или полной проверкой формата, включая активное содержимое PDF. Реальные хосты и MIME ответов поставщика в рамках локальной подготовки не проверены.

Фоновая задача в приложении планируется каждые 10 секунд при включённом модуле, обрабатывая максимум два вложения за вызов. Для каждого вложения предусмотрено до трёх попыток с паузой 30 секунд после ошибки. Захват работы действует 300 секунд; просроченная работа получает `lease_expired` и повторяется только пока не исчерпан лимит. GET-запросы не запускают загрузчик и не меняют очередь. Работу планировщика нужно проверить отдельно.

Ссылки на исходные файлы могут истекать. Ошибка и число попыток видны в ответах API; `failed` не означает, что ещё будет повтор после третьей попытки. URL хранится только внутри архива для ожидающего загрузки вложения и очищается после успеха; в GET-ответы он не попадает. При выключенных медиа вложение получает `disabled` без сохранения URL. Последующее включение медиа не загружает такие старые вложения автоматически, а повтор webhook не перезаписывает их.

## API читателя

Все маршруты требуют отдельного токена чтения и предназначены для `GET`. Токен не выдаёт доступ к бухгалтерским операциям или отправке WhatsApp-сообщений.

| Маршрут | Использование |
| --- | --- |
| `/api/furniture-reader/messages?chat_id=&after_id=&limit=` | Сообщения разрешённых чатов с курсором и ограничением количества. `chat_id` необязателен; если указан, ограничивает выдачу одним разрешённым чатом. Пустой `chat_id=` не равнозначен отсутствию параметра. |
| `/api/furniture-reader/attachments/<id>` | Доступ к сохранённому вложению после проверки разрешений на его чат. |
| `/api/furniture-reader/status` | Число сообщений, время последнего приёма и числа вложений по состояниям только в разрешённых для чтения чатах. |

`after_id` — целое число от `0`, по умолчанию `0`; `limit` — целое от `1` до `100`, по умолчанию `50`. Ответ сообщений имеет вид `{"messages": [...], "next_after_id": число}`. Сообщения идут по возрастанию локального `id`, выбираются строки с `id > after_id`. Курсор — последний возвращённый `id`, а при пустом результате — переданный `after_id`.

Каждое сообщение содержит `id`, `instance_id`, `chat_id`, `message_id`, `direction`, `sent_at` (Unix timestamp в секундах), `received_at` (ISO 8601 UTC), `message_type`, `text` и `attachment`. Вложение равно `null` или объекту с полями `id`, `filename`, `declared_mime_type`, `state`, `mime_type`, `size` (байты), `sha256`, `error_code`, `attempts`. До загрузки часть значений равна `null`. Возможные состояния: `pending`, `processing`, `failed`, `ready`, `disabled`, `unsupported`. Публичный ответ не содержит исходный JSON, URL загрузки, внутреннее имя/путь файла или отдельные поля имени/телефона отправителя.

Ответ `/status` содержит `message_count`, `last_received_at` и объект `attachments` с шестью счётчиками указанных состояний. До первого события возвращаются нулевые счётчики и `last_received_at: null`, без создания БД. Это статистика архива, а не полная проверка здоровья GREEN-API или планировщика.

`/attachments/<id>` выдаёт только `ready`-вложение из разрешённого чата. Ответ — скачивание `application/octet-stream` с исходным очищенным именем файла, без inline-предпросмотра. Для чужого, отсутствующего, ещё не готового или недоступного на диске вложения возвращается `404`. Все ответы модуля запрещают кеширование (`Cache-Control: no-store`) и MIME-sniffing.

Ошибки GET API возвращаются JSON-объектом с полем `error`: `404 Not found` при выключенном модуле или неразрешённом объекте, `503 Reader not configured` при неверной конфигурации чтения, `401 Unauthorized` при неверном токене, `400 Invalid pagination` при неверной пагинации, `503 Archive unavailable` при ошибке архива. `HEAD`/`OPTIONS` отклоняются защитой маршрутов с `405` при включённом модуле. Другие методы не поддерживаются; в полном приложении они могут быть отклонены общей авторизацией до ответа о неверном методе. Клиент должен использовать именно GET.

Клиент хранит курсор для выбранного способа чтения: общий при выдаче всех разрешённых чатов либо отдельно для каждого `chat_id`. Продвигать его нужно только после успешной обработки страницы. При расширении списка разрешений старые строки нового чата могут лежать до уже сохранённого курсора; их чтение требует отдельного согласованного запроса, а не обещания автоматической догрузки. Пустой ответ не доказывает отсутствие сообщений в WhatsApp: событие могло не поступить, быть отклонено или ещё не сохраниться.

Подключение к ассистенту — отдельная работа: требуется проверить, что конкретный интерфейс действительно поддерживает выбранный коннектор, передачу Bearer-заголовка и доступ к этим HTTPS-маршрутам. Само наличие API не означает, что произвольный API или MCP можно подключить в текущем интерфейсе. До такой проверки возможен только проверенный способ отдельного чтения; постоянное наблюдение и автоматические сводки не считаются настроенными.

## Отключение и откат

1. Выключить `FURNITURE_READER_ENABLED` и перезапустить сервис с обновлённой конфигурацией. Проверить `404` на API читателя и отсутствие новой работы мебельного архива/загрузчика. Webhook при этом возвращается к прежнему поведению; закрытый бухгалтерский список должен сохраняться, чтобы мебельные события не начали попадать в старый бухгалтерский маршрут.
2. При необходимости отозвать доступ клиента сменой отдельного токена чтения. При инциденте с входящей аутентификацией отдельно заменить мебельный webhook-токен после согласования с отправителем. Не использовать для этого смену полного токена GREEN-API или учётных данных бухгалтерского бота.
3. Оставить действующий бухгалтерский webhook и его список групп в проверенном состоянии. Если выполняется откат версии приложения, использовать последнюю проверенную версию и проверить продолжение существующей обработки.
4. Сохранить закрытый архив, вложения и резервную копию для разбирательства. Отключение модуля не следует считать удалением данных. Удаление архива — отдельная явно согласованная операция.
5. Перед повторным включением устранить причину, повторить проверки изоляции и учесть пропуск событий за время отключения. Не обещать автоматическое восстановление пропущенных сообщений.

## Ограничения

- Принимаются новые доставленные события после активации. Чтение всей старой переписки, загрузка истории и повторный импорт накладных в эту схему не входят; для них нужен отдельный согласованный план.
- Архив ограничен разрешёнными чатами и фактически поступившими событиями. Он не даёт доступа ко всему WhatsApp или группам, недоступным подключённому instance.
- При выключенных медиа фотографии и документы не становятся сохранёнными вложениями. Истёкшая ссылка, недоступный хост, превышение размера или исчерпанные повторы требуют отдельного разбора.
- OCR, распознавание накладных, поиск по содержимому и автоматические сводки не реализованы. Сохраняются текст/подпись и поддерживаемые вложения; голосовые сообщения не расшифровываются. Отдельного авторства участников группы в схеме нет. Эти возможности требуют отдельной реализации без доступа к бухгалтерским действиям.
- Текст сообщений и документов является внешними данными. Инструкции внутри них не меняют разрешения читателя и не дают ассистенту права отправлять сообщения или выполнять финансовые операции.
- Постоянная работа без Mac подтверждается только после проверки сервиса, тома, резервных копий, наблюдения за сбоями и реального подключения выбранного ассистента.
