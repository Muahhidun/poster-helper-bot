# MCP и OAuth: решение перед реализацией

Дата проверки официальных документов: 16 октября 2026 года.

**Историческая записка этапа выбора AS.** После этой записки пользователь выбрал Auth0 Free и разрешил локальную реализацию с фиктивными ключами/тестами. Актуальное состояние, ограничения и план активации: [Furniture MCP + Auth0](furniture_mcp_auth0.md). Ниже сохранено исходное обоснование решения; ожидание выбора провайдера больше не является блокером. Реальные tenant, OAuth-клиенты и grants по-прежнему не созданы.

## Что подтверждено

Показанная форма соответствует документированному подключению пользовательского MCP сервера. OpenAI поддерживает Streamable HTTP и OAuth; возможен заранее зарегистрированный OAuth-клиент. Его client ID/secret — учётные данные клиента OAuth, а не постоянный токен доступа к архиву. Точный redirect URI нужно взять из страницы управления создаваемым подключением. Подставлять предполагаемый callback нельзя. [OpenAI: подключение](https://developers.openai.com/api/docs/guides/custom-mcp-server), [OpenAI: авторизация](https://developers.openai.com/plugins/build/auth).

На дату проверки актуальная MCP-спецификация — `2026-07-28`. Она разделяет ресурсный сервер и сервер авторизации; допускает предварительную регистрацию клиента, рекомендует CIMD, а DCR оставляет как совместимый устаревающий вариант. Поэтому для первого частного подключения предлагается предварительно зарегистрированный клиент с PKCE S256, без собственного DCR/CIMD обработчика. [MCP: авторизация](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [регистрация клиента](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration).

Официальный Python SDK документирует v2 как текущую стабильную линию и требует Python 3.11+. Он подходит для транспорта и ресурсной части OAuth. Однако он не предоставляет готовые вход, согласие пользователя и выдачу токенов; встроенный `auth_server_provider` для новых серверов не рекомендуется. Реальный verifier должен проверять JWT либо обращаться к introspection выбранного AS. Точную версию SDK и совместимость зависимостей потребуется зафиксировать при реализации, без изменения библиотек бухгалтерского приложения. [SDK](https://py.sdk.modelcontextprotocol.io/), [SDK authorization](https://py.sdk.modelcontextprotocol.io/run/authorization/).

В текущем проекте есть Flask-сессия и `web_users` в бухгалтерской БД. Вход обновляет `last_login`, а создание `UserDatabase` запускает инициализацию/миграции. Это не OAuth Authorization Server. В просмотренном коде и requirements нет готовых OAuth discovery, клиентского реестра, consent/grants, PKCE или механизма отзыва OAuth-токенов. Существующий `FURNITURE_READ_TOKEN_SHA256` также не является OAuth и не должен приниматься MCP транспортом. Основание в коде: [вход сайта](../web_app.py), [бухгалтерская БД](../database.py), [конфигурация читателя](../furniture_reader/config.py).

## Решение, которое нужно согласовать

Предлагается **отдельный ресурсный MCP сервер на официальном Python SDK и готовый Authorization Server**, выбранный владельцем. MCP получает только доступ для чтения закрытого архива, без импорта `web_app`, `UserDatabase`, Gemini, Poster и обработчика WhatsApp.

SDK предоставляет ASGI-приложение с собственным lifecycle; это не Flask Blueprint. Отдельный процесс позволит сохранить прежний WSGI/Gunicorn запуск бухгалтерии. При этом `/mcp` использует HTTP POST для вызовов читающих инструментов: существующий GET API не становится MCP после переименования URL. [SDK ASGI](https://py.sdk.modelcontextprotocol.io/run/asgi/), [MCP Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).

Нужно одно из двух решений:

1. Подтвердить уже используемый OAuth/OIDC провайдер и его публичный issuer URL. Секреты в переписке не нужны.
2. Если такого провайдера нет — согласовать выбор управляемого сервиса либо отдельного самостоятельно размещаемого AS, его владельца и эксплуатационные расходы. Самостоятельно размещаемый AS тоже требует отдельной настройки, обновлений, резервирования и защищённого хранения.

До выбора невозможно честно подтвердить обработку `resource`, формат audience, срок жизни, немедленный отзыв, способ регистрации клиента и хранение grants. Создавать самодельный AS внутри финансового приложения, превращать существующий bearer в OAuth или включать no-auth не предлагается. Приостановка означает ожидающее решения условие задачи; отказа инструмента или неопределённого результата внешнего изменения нет.

## Требования к выбранному AS и ресурсному серверу

| Область | Проверяемое условие |
| --- | --- |
| Discovery | Ресурс публикует `/.well-known/oauth-protected-resource/mcp` с каноническим HTTPS `resource`, точным issuer и минимальными scopes; `401` указывает на metadata. AS публикует OAuth/OIDC discovery. |
| Code flow | Authorization Code + обязательный PKCE `S256`; metadata явно объявляет поддержку. AS проверяет точный зарегистрированный `redirect_uri`, связывает одноразовый code с клиентом, redirect URI и challenge. |
| Resource | Клиент передаёт `resource` на authorize и token; AS связывает его с audience и не выдаёт токен для произвольного ресурса. Ресурсный сервер проверяет этот audience при каждом запросе. |
| Issuer | Используется заранее доверенный issuer. Если объявлен RFC 9207, AS возвращает правильный `iss` и в успешных, и в ошибочных authorization responses. |
| Валидация | Проверяются подпись/JWKS либо доверенный ответ introspection, issuer, audience, `exp`, `nbf`, активность, subject и scopes. Отсутствующий/недействительный token — `401`; недостаточное право — `403`. Не брать URL ключей из недоверенного токена. |
| Область доступа | OAuth identity определяется парой `(issuer, subject)`. Client ID не подменяет пользователя. Сервер связывает identity с одним архивом и ожидаемым instance; итоговый список чатов — пересечение разрешений этой identity, списка приёма и списка чтения. Пустое пересечение закрывает доступ. |
| Отзыв | Предлагается online introspection без положительного кеша, если требуется немедленный отзыв. При JWT-only отдельного отзыва refresh grant недостаточно для немедленной недействительности уже выданного access token: нужен механизм denylist/introspection либо согласованное окно до `exp`. Ошибка проверки закрывает доступ. |
| Хранение | AS хранит коды/grants/refresh credentials защищённо и реализует их атомарное использование, срок жизни и отзыв. Для публичных клиентов refresh tokens ротируются. MCP не хранит bearer tokens и не пишет их в логи; необходимые AS credentials — только в защищённых настройках. |

Основание: [MCP discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery), [MCP security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations), [OpenAI auth](https://developers.openai.com/plugins/build/auth). Introspection без кеша и отдельное сопоставление identity с чатами — предложенная политика этого проекта, а не утверждение, что любой провайдер уже обеспечивает её.

## Предлагаемый минимальный контракт инструментов

Контракт ниже пока не реализован. Предлагаются два scope: `furniture.messages:read` и `furniture.attachments:read`. Все инструменты: `readOnlyHint=true`, `destructiveHint=false`, `idempotentHint=true`, `openWorldHint=false`, явная схема OAuth2. Сервер проверяет права при каждом вызове независимо от annotations и списка tools.

| Инструмент | Scope | Предлагаемое ограничение |
| --- | --- | --- |
| `list_chats` | `furniture.messages:read` | Только разрешённые caller чаты, до 50 за страницу; стабильный курсор. |
| `search_messages` | `furniture.messages:read` | Запрос 2–200 символов, до 20 результатов по умолчанию/50 максимум; курсор, ограниченное время SQL, ответ до 64 KiB. Только сохранённый текст/подписи, без OCR. |
| `read_message` | `furniture.messages:read` | Один ID в разрешённом чате, ответ до 128 KiB; метаданные вложения без исходного URL и локального пути. |
| `read_attachment` | Оба read scopes | Одно готовое вложение того же разрешённого чата, до 2 MiB исходных байтов за вызов. Более крупный файл возвращает только ограниченную информацию о превышении; автоматической загрузки/перекодирования/OCR нет. |

Последний лимит относится к будущему MCP-ответу, а не меняет текущий лимит безопасного загрузчика архива. Возможность отображения изображений/PDF конкретным клиентом проверяется отдельно. Публичные ссылки на файлы и передача OAuth-токена стороннему URL исключены. Полный доступ к большим файлам потребует отдельно проверенного механизма; он здесь не обещан.

Существующие `ArchiveStore.list_messages`, `get_attachment` и `status` используют чтение SQLite без инициализации БД. Для MCP ещё нужны отдельные ограниченные запросы списка чатов, поиска и одного сообщения. Нынешние read-запросы фильтруют по `chat_id`, но не по `instance_id`; будущие MCP-запросы должны также ограничиваться серверно назначенным instance, чтобы смена инстанса или архив с историческими строками не расширяли OAuth-доступ. Названия групп и отдельные сведения об авторах не хранятся и не должны выдумываться.

Проверки приватного пути, владельца/прав/ссылок файла и готовности вложения должны сохраниться. Чтение не запускает media worker, не захватывает задания и не обращается к GREEN-API.

## Проверки после выбора AS

Сначала локальные тесты через HTTP/ASGI транспорт на синтетическом архиве и фиктивной identity: `server/discover` для версии 2026-07-28, `initialize` отдельно для совместимости с прежними клиентами, `tools/list`, `tools/call`; metadata/401 challenge; неподписанный, просроченный, ещё не действующий, отозванный токен; неверные issuer/audience/subject/scopes; пустые и чужие chat scopes; пагинация, лимиты и недоступное вложение. Поддерживаемые версии нужно согласовать с фактическим OpenAI-клиентом и выбранным релизом SDK. Отдельно — отсутствие вызовов бухгалтерии/отправки и отсутствие изменений файлов архива. In-memory MCP client сам по себе HTTP-авторизацию не проверяет.

Для выбранного AS потребуются проверки code replay, неправильного PKCE verifier, отсутствующего S256, несовпадающих redirect URI/resource, увеличения scopes при refresh, отзыва и повторного использования refresh token, ротации ключей и недоступности AS. Использовать официальную тестовую конфигурацию выбранного провайдера; фиктивный verifier не доказывает корректность этих потоков.

На этом этапе добавлен только данный документ. Новых MCP/OAuth тестов нет, поскольку транспорт и AS не реализованы. Последняя проверка неизменённого архива: 177 новых тестов прошли; в общем наборе 202 прошли и 2 старых упали, обе ошибки воспроизведены с исходным `web_app.py` (`25 passed, 2 failed`). Это не результат тестирования OAuth.

## Последующая активация: действия для отдельного согласования

1. Выбрать/подтвердить AS, место размещения и ответственного. Согласовать возможную оплату и передачу identity данных провайдеру. Затем локально реализовать verifier и контракт, зафиксировать версии, выполнить указанные тесты и независимый обзор.
2. Согласовать размещение MCP endpoint и доступ к постоянному архиву только для чтения. Проверить доступность тома для выбранной топологии; локальный SQLite не является общим томом независимых Railway реплик. Подготовить HTTPS, backup/restore и мониторинг отдельно от бухгалтерских credentials.
3. Отдельно разрешить создание реального OAuth client/resource/scopes, серверного сопоставления identity с чатами, ключей и защищённых настроек; определить срок жизни access/refresh tokens и способ отзыва. Эти действия сейчас не выполнены.
4. Отдельно разрешить публикацию кода и настройку подключения в форме MCP. Выбрать OAuth, взять из формы точный redirect URI и зарегистрировать только его; проверить discovery/PKCE/resource. Не включать no-auth и не вставлять архивный API-токен вместо OAuth.
5. После отдельного разрешения выполнить реальный вход/consent и тест из разговора: чтение одного согласованного сообщения/вложения, отказ по чужому чату, отзыв и повторный отказ. Только после этого можно заявлять проверенную совместимость конкретного подключения. Создание plugin и OAuth grant являются действиями активации.

Публикация, production/GREEN-API настройки, реальные ключи/учётные записи/grants и финансовые операции не выполнялись. Постоянное наблюдение и автоматические сводки этим документом не настроены.
