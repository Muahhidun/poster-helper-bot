# Чтение мебельного архива через HTTPS

Реализовано локально в ветке `codex/furniture-http-backend`. Код не опубликован,
production и реальные чаты не включены. Остановленный synthetic deployment не
требуется для этих проверок и не перезапускается.

## Разделение процессов и данных

Действующий `poster-helper-bot` остаётся единственным получателем GREEN-API
webhook. Подготовленный `furniture_reader` пишет только разрешённые мебельные
события в собственный SQLite `archive.sqlite3` и каталог `media`. Это отдельное
хранилище, без финансовых таблиц и `UserDatabase`. Бухгалтерские группы сохраняют
прежний маршрут. Мебельные сообщения не попадают в Gemini/Poster и не вызывают
отправку WhatsApp.

Отдельный MCP-процесс может читать этот архив двумя способами:

- `sqlite` — прежний режим с локальным каталогом и read-only SQLite.
- `http` — новые асинхронные GET-запросы к фиксированному HTTPS API архива.

HTTP-режим не открывает локальные файлы и не требует тома у MCP-сервиса. Он не
получает GREEN-API, Poster, Telegram, Gemini или бухгалтерские credentials.
Нужен новый отдельный токен только мебельного чтения: его SHA-256 хранится у
источника в `FURNITURE_READ_TOKEN_SHA256`, исходное значение — в защищённой
переменной MCP-сервиса `FURNITURE_MCP_ARCHIVE_TOKEN`. Webhook-токен должен быть
другим. Не помещайте эти значения в репозиторий, переписку, URL или логи.

## Конфигурация HTTP backend

Существующие issuer, resource URL, client ID, owner subject, instance и три
вложенных списка разрешённых чатов остаются обязательными. Добавлены:

| Переменная | Значение |
| --- | --- |
| `FURNITURE_MCP_ARCHIVE_BACKEND` | Строго `sqlite` (по умолчанию) или `http`. Ошибка закрывает запуск. |
| `FURNITURE_MCP_ARCHIVE_URL` | В HTTP-режиме один точный `https://host/api/furniture-reader/mcp`, без порта, credentials, query, fragment или завершающего `/`. |
| `FURNITURE_MCP_ARCHIVE_TOKEN` | Отдельный read-token 32–512 печатных ASCII-символов без пробелов. Не выводится в `repr` настроек. |

`FURNITURE_STORAGE_DIR` в HTTP-режиме не используется и не проверяется. В SQLite
режиме требования к закрытому постоянному каталогу сохраняются. Выключенный MCP
по-прежнему не валидирует настройки, не создаёт HTTP-клиент и не обращается к диску.

Сам источник использует существующие настройки `furniture_reader`: включённый
флаг, непустые непересекающиеся мебельный и бухгалтерский списки, точный instance,
два разных хеша токенов и допустимый storage path. Список чтения должен оставаться
подмножеством списка приёма. Основной сайт публичный: эти пути тоже внешне
адресуемы, но каждый запрос требует отдельный read-token. Использование
межсервисного URL само по себе не делает маршруты недоступными из интернета.

## GET-контракт источника

Все пути ниже имеют префикс `/api/furniture-reader/mcp` и используют
`Authorization: Bearer …`. Никаких write-методов или токенов в query.

| Путь | Аргументы |
| --- | --- |
| `/chats` | `after_chat_id` (по умолчанию пустой), `limit` 1–50 (50) |
| `/search` | Необязательный `chat_id`; `after_id` ≥0 (0); `limit` 1–50 (20); искомый текст передаётся отдельным заголовком. |
| `/messages/<id>` | Положительный числовой ID; без query |
| `/attachments/<id>` | 32 строчных hex-символа; без query |

MCP формирует `X-Furniture-Archive-Scope` только из своей серверной конфигурации:
JSON с `instance_id` и отсортированным уникальным массивом `chat_ids`. Этот
заголовок не является аргументом инструмента. Источник требует совпадения instance
и проверяет, что запрошенный набор — непустое подмножество разрешённых для чтения
чатов. Чужая область возвращает `404`, некорректная — `400`. Заголовок ограничен
4096 ASCII-байтами и максимум 100 чатами. Слишком большая конфигурация HTTP-режима
отклоняется при запуске, вместо ошибки размера заголовка уже во время чтения.

Текст поиска передаётся как ASCII JSON-строка в `X-Furniture-Archive-Query`
(2–200 символов после декодирования). Он не помещается в URL и обычную строку
access log. Настройки логирования должны также исключать значения этих заголовков.

Источник применяет один и тот же `ArchiveReader` к локальному SQLite. Он читает
через `mode=ro`, `query_only`, проверяет идентификатор/версию схемы и не создаёт
отсутствующий архив. Ожидание блокировки начинается с лимита 250 мс уже при
открытии; бюджет запроса дополнительно ограничен временем и шагами SQLite.

Ответ `200` — JSON с `version: 1`, точными `instance_id`/`chat_ids` и `result`.
Поля результата соответствуют четырём MCP-инструментам. Готовое вложение
передаётся как `data_base64` вместе с безопасными метаданными, размером и SHA-256.
Исходные download URL, локальные пути и полные webhook payload не выдаются.
Отсутствующий объект — `404`; отказ архива — обезличенный `503`. Методы кроме GET,
дублирующиеся или неизвестные query-аргументы отклоняются. Ответы запрещают кеширование.

## Границы HTTP-клиента

Клиент не следует редиректам, не использует переменные proxy, cookies или
автоматическую авторизацию HTTP-клиента. TLS-проверка остаётся включённой. На
запрос, включая потоковое получение, действует общий дедлайн 5 секунд.
Сжатые ответы запрещены; размер ограничен и по Content-Length, и по полученным
байтам. Неизвестные поля, повторяющиеся JSON-ключи, несоответствующая область,
чужие строки, неверные курсоры, ID, размер, MIME или SHA-256 закрывают выдачу.
Сбой источника не превращается в успешный пустой список. Подробности HTTP-ошибок
и credentials не попадают в MCP-ответ.

Вложения сохраняют прежний предел MCP **2 MiB** и поддержку JPEG/PNG/WebP/PDF.
Большие файлы возвращают состояние `too_large`, отсутствующие или повреждённые
на диске — `unavailable`; GET не скачивает их заново и не двигает очередь. OCR,
история до включения, обработка редактирования/удаления и голосовая расшифровка
не добавлены. Тексты сообщений остаются недоверенными данными.

## Постоянное хранение и план запуска

Существующее хранилище можно использовать без доступа к бухгалтерской БД, если
это собственный закрытый каталог мебельного архива на постоянном томе. Для
проверки пригодности Railway нужны только метаданные mount path, свободного
места, владельца каталога и числа реплик. Содержимое финансовой базы и секреты
для этого не нужны. Наличие подходящего существующего тома **пока не проверено**.

Предлагаемый минимальный вариант: постоянный volume у основного сервиса,
`FURNITURE_STORAGE_DIR=/furniture-data/archive`, отдельный MCP-сервис без volume.
Если основной сервис уже использует несовместимый том или несколько реплик,
его инфраструктуру ради этого не менять: потребуется отдельный collector и
новое рассмотрение переноса событий. Railway допускает один volume на service;
volume ограничивает replicas и создаёт короткое окно простоя при redeploy.
[Документация volumes](https://docs.railway.com/volumes/reference).

Перед добавлением нового тома worker сначала опубликовать и развернуть защиту
путей в `config.py`, затем установить `FURNITURE_VOLUME_MOUNT_PATH=/furniture-data`.
Только этот точно совпадающий mount исключается из автоматического выбора
бухгалтерских каталогов: `users.db`, справочники, storage и logs сохраняют прежние
пути. Обычный существующий бухгалтерский том продолжает работать как раньше.
Не прикреплять мебельный том к старой версии: Railway автоматически добавляет
`RAILWAY_VOLUME_MOUNT_PATH`, и прежний код переместит по нему бухгалтерские пути.

До активации нужны: сверка с актуальным production commit, минимальный образ
отдельного MCP, точная группа, защищённый ввод токенов, постоянный том,
согласованный срок хранения, окно обновления и адресный rollback. Минимальный
запуск может быть отдельно согласован без backup и жёсткого денежного лимита;
это не означает наличие защиты от потери архива или превышения расходов.
Для последующего резервирования проверять восстановление SQLite/media.
Не копировать живой SQLite без учёта журнала; использовать SQLite backup API или
проверенный согласованный snapshot. Эти эксплуатационные функции данный backend
сам по себе не создаёт.

Мебельная ветка webhook сейчас возвращает `503` при отказе записи. Локальный тест
проверяет, что бухгалтерская ветка продолжает выбирать прежнюю очередь, но не
доказывает независимость доставки у GREEN-API. До запуска нужно проверить, не
блокируют ли повторы мебельного события общий поток. При необходимости отдельно
согласовать bounded spool или потерю мебельного события с метрикой; не менять
этот компромисс молча. Не добавлять второй ReceiveNotification/DeleteNotification
consumer. [Приём GREEN-API](https://green-api.com/en/docs/api/receiving/technology-http-api/).

Текущий webhook должен передавать корректный Bearer-заголовок. Если его нет,
потребуется отдельное согласование `webhookUrlToken`: `SetSettings` по документации
перезапускает instance. URL/флаги, очередь, credentials и настройки GREEN-API в
этой локальной работе не изменяются.
[SetSettings](https://green-api.com/en/docs/api/account/SetSettings/).

Для реальных данных нужны отдельный согласованный production audience/grant,
точные chatId и owner, два read scopes, пользовательский OAuth consent и отдельные
read credentials. Тестовый grant не расширяется автоматически. Текущие TTL900 и
отключённый refresh/offline означают возможную повторную авторизацию; постоянный
архив не означает постоянное фоновое чтение ассистентом или автоматические сводки.

## Расчёт расходов

Сценарий на 30 суток при текущих тарифах Railway, USD:

| Компонент | Допущение | В месяц |
| --- | --- | ---: |
| Отдельный MCP | Средние 0.25 GB RAM + 0.1 vCPU | 4.50 |
| Дополнительная работа archive/media | Средние 0.1 GB RAM + 0.05 vCPU | 2.00 |
| Постоянный том | 5 GB занято | 0.78 |
| Исходящий трафик | 1 GB | 0.05 |
| Итого сценария | Без backup/OCR и без превышения средних нагрузок | **7.33** |

Это расчёт потребления, не долларовый лимит. При непрерывных 1 vCPU + 0.5 GB RAM
только MCP compute ≈ $25.01/30 суток. Существующий Pro включает $20 суммарного
usage; дополнительный счёт зависит от всего workspace. Нового платного Railway
тарифа не требуется. Проверить, что Auth0-функции останутся на Free после trial;
платное повышение требует отдельного согласия. Существующий GREEN-API тариф не
меняется. [Тарифы Railway](https://railway.com/pricing).

Не ставить маленький workspace hard limit: он может остановить бухгалтерского
бота вместе с другими workload. Нужны отдельное наблюдение и согласованный бюджет
мебельной части. Автоматизации этим изменением не создаются.
[Cost Control](https://docs.railway.com/pricing/cost-control).

## Локальная проверка

Использовать отдельное временное virtualenv с `requirements-furniture-tests.txt`,
не устанавливать зависимости в работающий сервис. Два автономных runner очищают
окружение и запрещают внешнюю сеть; финансовая тестовая конфигурация направляет
`users.db`, storage и logs в новый временный каталог и отключает dotenv.

```text
<test-python> -B scripts/run_furniture_mcp_tests.py tests/furniture_mcp -q
<test-python> -B scripts/run_furniture_tests.py tests/furniture_reader -q
<test-python> -B scripts/run_furniture_tests.py tests/test_whatsapp_webhook.py tests/test_whatsapp_queue.py --synthetic-whatsapp-catalog -q
```

Окончательный прогон HTTP/MCP: 521 тест пройден; furniture_reader: 210 тестов
пройдено. Включены настоящий Flask API через MockTransport, локальная RSA/JWKS
авторизация, JPEG/PNG/PDF представление, запрет чужой области и повреждённых
ответов, недоступность источника, отсутствие write-side effects и открытие
сохранённого архива новым Python-процессом. Это локальные проверки, а не
подтверждение реального volume, GREEN-API доставки или production запуска.
Для старых WhatsApp-тестов флаг копирует только пять синтетических строк из
`tests/fixtures/synthetic_whatsapp_catalog` во временный каталог. Строки составлены
по данным уже существующих тестов; пользовательские справочники не читаются.

Упаковка постоянного HTTP MCP находится в `deploy/production`. Экспортирует 14
разрешённых файлов без финансового приложения, dotenv и synthetic runtime.
Отдельная проверка подтвердила импорт выключенного и HTTP ASGI factory из этого
экспорта. Четыре теста путей `test_config_paths.py` подтвердили сохранение
бухгалтерских каталогов при добавлении мебельного тома и прежнее поведение для
обычного тома. Полная сборка контейнера и реальное развёртывание ещё не проверены.
